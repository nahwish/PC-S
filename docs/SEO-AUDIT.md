## Resumen ejecutivo

El proyecto tiene una base técnica sólida (Next.js 15 App Router, `next/image`, semántica HTML parcial, modal accesible), pero **no tiene configuración SEO real**. El metadata es el boilerplate de `create-next-app`, no existe `robots.txt` ni `sitemap.xml`, y la página principal se renderiza completamente en el cliente, lo que limita la indexación del contenido por los crawlers.

| Área | Estado |
|---|---|
| Metadata (title/description) | ❌ Crítico |
| Open Graph / Social | ❌ Ausente |
| Estructura HTML semántica | ⚠️ Parcial |
| Indexabilidad (SSR/SSG) | ❌ Crítico |
| Archivos de rastreo (robots/sitemap) | ❌ Ausente |
| Accesibilidad (a11y) | ✅ Buena base |
| Imágenes | ✅ Bien implementado |
| Fuentes | ✅ Optimizado |
| Rutas individuales por entidad | ❌ Ausente |

## Problemas críticos

### C1. Metadata de boilerplate sin personalizar — ❌
**Archivo:** `app/layout.tsx` — líneas 16-19

```tsx
export const metadata: Metadata = {
  title: "Create Next App",          // ← texto literal de plantilla
  description: "Generated by create next app",  // ← texto literal de plantilla
};
```

**Impacto:** El `<title>` es el factor on-page más importante para SEO. "Create Next App" no describe ni la temática del sitio. La description aparece en los SERPs y en las vistas previas en redes sociales.

**Corrección sugerida:**
```tsx
export const metadata: Metadata = {
  title: {
    default: "Pokédex — Explora todos los Pokémon",
    template: "%s | Pokédex",
  },
  description:
    "Pokédex completa con más de 1000 Pokémon. Filtra por tipo, consulta estadísticas y descubre todos los detalles de cada Pokémon.",
};
```

---

### C2. Sin Open Graph ni Twitter Cards — ❌
**Archivo:** `app/layout.tsx`

No existe ninguna propiedad `og:*` ni `twitter:*`. Cuando se comparte la URL en WhatsApp, Slack, Twitter/X, LinkedIn o Facebook, el preview mostrará información genérica o nula.

**Corrección sugerida:**
```tsx
export const metadata: Metadata = {
  openGraph: {
    title: "Pokédex — Explora todos los Pokémon",
    description: "Pokédex completa con filtro por tipo y estadísticas.",
    url: "https://tu-dominio.com",
    siteName: "Pokédex",
    images: [{ url: "/og-image.png", width: 1200, height: 630 }],
    locale: "es_ES",
    type: "website",
  },
  twitter: {
    card: "summary_large_image",
    title: "Pokédex — Explora todos los Pokémon",
    description: "Pokédex completa con filtro por tipo y estadísticas.",
    images: ["/og-image.png"],
  },
};
```

---

### C3. `lang="en"` incorrecto — ❌
**Archivo:** `app/layout.tsx` — línea 27

```tsx
<html lang="en">  // ← incorrecto
```

La interfaz está en **español** (labels, placeholders, estados de carga, textos del modal). Los motores de búsqueda usan este atributo para determinar el idioma del contenido y mostrarlo a las audiencias correctas. Los lectores de pantalla también lo usan para la pronunciación.

**Corrección:**
```tsx
<html lang="es">
```

---

### C4. Página principal completamente client-side — ❌
**Archivo:** `app/page.tsx` — línea 1

```tsx
"use client"
```

**Impacto:** Todo el contenido (la grilla de pokémons) se genera en el navegador del usuario. Cuando un crawler de Google visita `/`, recibe un HTML casi vacío. Aunque Googlebot puede ejecutar JavaScript, la indexación de contenido cliente-side es:
- Más lenta (deferred indexing)
- Menos fiable
- Penalizada vs. contenido SSR/SSG

**Causa:** La directiva `"use client"` existe porque se usan hooks (`useEffect`, `useCallback`). La solución correcta es extraer los hooks a un componente cliente hijo y mantener el `page.tsx` como Server Component.

**Impacto adicional:** No hay contenido indexable por pokémon individual. Google no puede indexar "Bulbasaur" porque no tiene URL propia.

---

### C5. Sin `robots.txt` — ❌
**Directorio:** `public/` (ausente)

El archivo no existe. Sin él, los crawlers asumen permisos totales, lo cual no es necesariamente un problema, pero sí indica falta de control SEO deliberado. La referencia en `docs/DECISIONS.md` indica que estaba planeado.

**Solución:** Crear `public/robots.txt` o usar la API de Next.js en `app/robots.ts`:
```ts
// app/robots.ts
import { MetadataRoute } from "next"
export default function robots(): MetadataRoute.Robots {
  return {
    rules: { userAgent: "*", allow: "/" },
    sitemap: "https://tu-dominio.com/sitemap.xml",
  }
}
```

---

### C6. Sin `sitemap.xml` — ❌
**Directorio:** `public/` (ausente)

No existe. Los sitemaps aceleran la indexación y son especialmente importantes en sitios con mucho contenido (una Pokédex puede tener 1000+ URLs si existen rutas individuales).

**Solución cuando existan rutas individuales:**
```ts
// app/sitemap.ts
import { MetadataRoute } from "next"
export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  // Generar entradas por cada pokémon
}
```

---

### C7. Sin `<h1>` en ninguna página — ❌
**Archivo:** `app/page.tsx` y todos los componentes

La página principal no tiene ningún `<h1>`. Los motores de búsqueda asignan un peso semántico especial al `<h1>` para entender el tema principal de la página.

**Corrección sugerida:** Agregar un `<h1>` visible o visualmente oculto (técnica SR-only):
```tsx
<h1 className="sr-only">Pokédex — Todos los Pokémon</h1>
// o visible, como parte del diseño del header/nav
```

---

### C8. Sin rutas individuales por Pokémon — ❌
**Directorio:** `app/` (ausente `pokemon/[name]/`)

Toda la aplicación vive en `/`. Google no puede indexar "Pikachu" como una entidad separada. No hay URLs únicas, no hay `<title>` por pokémon, no hay posibilidad de aparecer en búsquedas de tipo "Pikachu stats" o "Charizard tipos".

**Solución a largo plazo:** Crear `app/pokemon/[name]/page.tsx` con `generateStaticParams` + `generateMetadata`.

## Mejoras moderadas

### M1. Bug en `aria-label` de `Contenedor` — ⚠️
**Archivo:** `app/components/base/card/Contenedor.tsx` — línea 20

```tsx
// Código actual (bug)
const arealLabel = `${pokemon?.name} ? Carta de ${pokemon?.name}, tipo ${pokemon?.types.map(...).join(", ")}: '`;
```

El `?` es texto literal en el template string, **no es un operador ternario**. El resultado sería una cadena como `"bulbasaur ? Carta de bulbasaur, tipo grass, poison: '"`, con el signo `?` y el `'` finales literales.

**Corrección:**
```tsx
const ariaLabel = pokemon?.name
  ? `Carta de ${pokemon.name}, tipo ${pokemon.types.map((t) => t.type.name).join(", ")}`
  : "Carta de Pokémon";
```

---

### M2. `next.config.ts` usa API `domains` deprecada — ⚠️
**Archivo:** `next.config.ts` — línea 4

```ts
images: {
  domains: ['raw.githubusercontent.com'],  // ← deprecado desde Next.js 13
}
```

`domains` está deprecado en favor de `remotePatterns`, que es más seguro y explícito.

**Corrección:**
```ts
images: {
  remotePatterns: [
    {
      protocol: "https",
      hostname: "raw.githubusercontent.com",
      pathname: "/**",
    },
  ],
},
```

---

### M3. Sin `canonical` URL — ⚠️
**Archivo:** `app/layout.tsx`

Sin una URL canónica definida, si el sitio puede accederse desde múltiples dominios (www/no-www, http/https), Google puede considerar el contenido como duplicado.

**Corrección:**
```tsx
export const metadata: Metadata = {
  alternates: {
    canonical: "https://tu-dominio.com",
  },
};
```

---

### M4. Sin favicon personalizado — ⚠️
**Directorio:** `app/` (solo existe el favicon de Next.js por defecto)

El favicon es un elemento de branding importante en los resultados de búsqueda (aparece en los SERPs de Google al lado del nombre del sitio).

**Solución:** Crear `app/favicon.ico` y opcionalmente `app/icon.png` con un icono de Pokémon/Pokébola.

---

### M5. `console.log` en producción — ⚠️
**Archivo:** `app/components/ui/nav/Nav.tsx` — líneas 22 y 32

```tsx
console.log("busqueda", tipo)
console.log("Resultado", listaPokemonsPorTipo)
```

Aunque no afecta directamente al SEO, viola las convenciones del proyecto y degrada la experiencia de auditoría de Best Practices en Lighthouse (penaliza la categoría).

---

### M6. `page.tsx` duplica lógica de `Nav.tsx` — ⚠️
**Archivos:** `app/page.tsx` líneas 15-20 y `app/components/ui/nav/Nav.tsx` líneas 12-17

La función `getPokemons` está definida en ambos archivos con lógica idéntica. Esto no afecta directamente al SEO pero sí a la mantenibilidad y puede generar race conditions en la carga inicial.

---

### M7. `<html>` sin atributos de internacionalización — ⚠️
**Archivo:** `app/layout.tsx`

No hay `dir="ltr"`, que aunque implícito, es buena práctica para accesibilidad y herramientas de traducción.

---

### M8. Sin `<meta name="theme-color">` — ⚠️
**Archivo:** `app/layout.tsx`

Afecta la experiencia móvil (color de la barra de estado en Android/Chrome). Next.js lo soporta en el objeto `metadata`:
```tsx
themeColor: "#FBBF24",  // amarillo Pokémon
```

---

### M9. Sin `<meta name="viewport">` explícita — ⚠️
**Archivo:** `app/layout.tsx`

Next.js lo agrega automáticamente, pero no está bajo control explícito. Para proyectos que necesiten control fino (e.g., prevenir zoom en iOS):
```tsx
viewport: {
  width: "device-width",
  initialScale: 1,
},
```

---

### M10. `aria-labelledby` redundante en `<select>` — ⚠️
**Archivo:** `app/components/ui/nav/Nav.tsx` — línea 49

```tsx
<select id='tipoSelect' aria-labelledby='tipoSelect'>
```

`aria-labelledby='tipoSelect'` apunta al propio `<select>` (mismo `id`), en lugar del `<label>`. El `<label htmlFor='tipoSelect'>` ya lo asocia correctamente. El `aria-labelledby` aquí es redundante e incorrecto en su referencia.

**Corrección:** Eliminar `aria-labelledby` del `<select>`, el `<label>` con `htmlFor` ya es suficiente.

## Mejoras menores

### m1. Sin datos estructurados (JSON-LD / Schema.org) — ℹ️
No hay marcado de Schema.org. Para una Pokédex, podrían aplicarse:
- `ItemList` en la página de listado
- `Thing` o `CreativeWork` para cada Pokémon individual (cuando existan rutas propias)

Esto permite Rich Snippets en Google (resultados enriquecidos).

---

### m2. Sin `preconnect` a dominios externos — ℹ️
**Archivo:** `app/layout.tsx`

Las peticiones a `pokeapi.co` y `raw.githubusercontent.com` pagan el costo del handshake TCP+TLS en la primera llamada. Agregar `preconnect` en el metadata de Next.js reduce este coste:

```tsx
export const metadata: Metadata = {
  // ...
}
// En layout.tsx, dentro del <head>:
<link rel="preconnect" href="https://pokeapi.co" />
<link rel="preconnect" href="https://raw.githubusercontent.com" />
```

En Next.js App Router, esto se hace añadiéndolos en el `<head>` del RootLayout.

---

### m3. Sin `generateMetadata` preparado para rutas dinámicas — ℹ️
**Relevante cuando existan:** `app/pokemon/[name]/page.tsx`

Cuando se creen rutas individuales por Pokémon, cada una necesita su propio `<title>` y `description` dinámicos:

```tsx
export async function generateMetadata({ params }: { params: { name: string } }): Promise<Metadata> {
  const pokemon = await getPokemonByName(params.name)
  return {
    title: `${pokemon.name} — Pokédex`,
    description: `Descubre todos los datos de ${pokemon.name}: tipos, estadísticas, habilidades y más.`,
  }
}
```

---

### m4. Imagen `psy.png` sin descripción en el nombre de archivo — ℹ️
**Archivo:** `public/psy.png`

Los nombres de archivo de imágenes aportan señales SEO menores. `psy.png` no es descriptivo. Un nombre como `empty-state-psyduck.png` sería más correcto.

---

### m5. Sin OG image estática — ℹ️
No existe ninguna imagen en `public/` destinada a ser el preview social del sitio (1200×630px). Crear un `og-image.png` mejora el CTR en redes sociales.

Next.js 15 también soporta `app/opengraph-image.tsx` para generarlas dinámicamente.

---

### m6. Título de la pestaña no cambia con el filtro activo — ℹ️
**Archivo:** `app/page.tsx`

Cuando el usuario filtra por tipo "Fuego", el `<title>` de la pestaña sigue siendo el mismo. En una SPA con rutas dinámicas esto no sería un problema, pero si se implementan query params (`/?tipo=fire`), se podría usar `generateMetadata` con `searchParams` para actualizar el título.
